# 设计上的关键决策

> 面向维护者。这些决策来自对真实 rug 手法的调研，直接决定检测准不准。
> 每一条都对应一个**具体的误判**，不是抽象的架构偏好。
>
> ⚠️ 改代码前请先读对应小节。许多「看起来啰嗦」的写法是为了避开
> 实测过的错误结论。

### 0. 集中度这个数字必须能被读者自己加出来

报告里 `Top10 集中度 = 38.2%` 单独出现时无法核对：38.2% 是哪些地址？被剔除的是哪些？
所以界面把**前 20 大持仓逐行列出**（`metrics.topHolders`），每行给：地址、数量、
占总供应量比例、分类、以及**是否计入集中度**。

界面上的等式是**两步**，因为集中度是「占流通盘」：

```
Top10 集中度 38.2% = 下表「计入」前 10 行合计 8.20%（占总供应） ÷ 流通盘 21.45%（占总供应）
```

这是一个**真等式**（有测试锁住 `sum / circulatingPct × 100 === top10Pct`），
读者按计算器一除就能核对。**不要写成「合计 = Top10」** —— 那是把两个分母混着用，
正是 §18 修掉的那个 bug。

两个必须说清楚的边界：

- 链上 RPC 的 `getTokenLargestAccounts` 只返回前 20 个持仓账户，所以这 20 行是
  「**能核对到的全部**」，不代表只有 20 个持有人。**更深的分布**改用
  `getProgramAccounts` 全量枚举，见下面的 §17（几千到几万行不做逐行渲染）。
- 前 20 行里被剔除的（池 / 销毁 / 锁仓）如果超过 10 行，「计入」的行就不够 10 行，
  等式会失效 —— 因此实现会在必要时**往后补几行**，保证计入的行至少有 10 行。

分类里有一类是为了这张表专门拆出来的：`related`（**与部署者关联的钱包** ＝
创建交易的付款方、给 creator 首笔交易出资的钱包）。它**计入集中度**（能随时卖出），
但绝不能显示成「散户」—— 它出钱发币、常常还持有 LP（实测 `9raUVuze…pump` 的创建钱包
持有 0.37% 代币 + 10.8% 全池 LP）。`devClusterPct` 也把这类钱包与 creator 合并计算。

### 1. 池地址必须**推导**出来，不能靠正则猜 —— 最大的误报源

bonding curve / AMM pool 天然持有大部分供应量。不剔除，任何正常项目都会被算成
「Top10 控盘 80%」。

真实池地址是**随机 base58 字符串**，用 `/pool|vault|amm/` 这类正则去匹配
**几乎永远匹配不到** —— 只会让人误以为已经处理过了。所以 `pools.ts` 用确定性推导：

- pump.fun bonding curve PDA：`seeds = ["bonding-curve", mint]`
- **池的 ATA**：池持有代币用的是它的 associated token account，
  只认池地址会漏掉真正的持仓账户
- DexScreener 的 `pairAddress`（AMM 池地址的直接来源）
- RugCheck 的 `market.pubkey / liquidityA / liquidityB`：**真实存在**的池与金库账户
  （Raydium v4 之类独立 vault 只有它能给出）
- 持仓匹配时 **owner 与 token account 任一命中即算池**（只看 owner 会漏掉金库）

曾经还推导过 PumpSwap 池 PDA（`seeds = ["pool", index, creator, …]`）。
实测该推导对真实代币算出的地址在链上**并不存在**（建池者是迁移权限账户，
不是代币创建者）—— 一串「看起来很像池」的随机地址。未经校验的推导比没有更糟，
已删除。

`pools.test.ts` 锁住了这一点：同一份数据，认不出池就会误报庄家控盘。

### 2. 池地址不能靠「谁在卖币」来推断 —— 会把 dev 的筹码抹掉

看起来合理的一个启发式：买单里把代币交出来的账户就是池。
**这是错的**，而且错得很危险 —— 「AMM 池提供流动性」和「dev 在砸盘」
在成交数据里长得一模一样。

实测后果：某代币 creator 持有 **46%** 供应量，因为频繁卖出而被判成「池」
并从集中度里剔除，报告显示「持仓分布健康」，把一个高度控盘的币
**判成了安全**。这是比误报更糟的一类错误 —— 误报只是吓跑用户，
漏报会让人真的亏钱。

所以池地址只认**确定性推导**与**权威数据源**：PDA 推导、DexScreener 的 pair 地址、
RugCheck 给出的池与金库账户。
漏掉池会让集中度偏高（已在 warnings 里如实说明），这比抹掉真实筹码安全得多。

### 3. 「已清仓」只能由链上余额判定，不能由流水比例判定

同样是实测踩出来的：creator 用流水口径算出「卖出/买入 = 100%」，
但**链上余额还有 27.6% 供应量**，于是报出「部署者已清仓」的硬否决 ——
与事实完全相反。

原因：交易历史窗口有限（只取最近 100 笔），建仓与减仓可能落在不同窗口，
比例自然会失真。**余额是事实，流水只是推断。**
因此 `devFullyExited` 是三态的：`true` 已确认清仓 / `false` 已确认未清仓 /
`undefined` 无法确认。**只有 `true` 才允许触发硬否决。**

### 4. Token-2022 本身不是风险信号

想当然的判断是「pump.fun 走经典 SPL Token，用 Token-2022 就是仿冒」。
**实测发现新版 pump.fun 代币本身就发行在 Token-2022 上**（带 metadata_pointer 扩展）。
按老假设写会把**每一个正常新币**都打上 high 风险 —— 模型直接失去区分度。

真正的风险在扩展内容：`transferHook` / `permanentDelegate` 这类能限制卖出
或转走持币的扩展才是要害，逐项检查即可。

### 5. 未知 ≠ 安全，也 ≠ 危险 —— 本项目最花心思的部分

真实数据源经常只给一部分数据。把缺失当成 0，会得到两种致命错误：

- **把缺失当「安全」** → 报告显示绿色「低风险」，用户以为体检过了
- **把缺失当「危险」** → 凭空报出高风险，用户被吓跑

因此：每个分析器在数据缺失时返回 `available: 0` 并说明缺失原因，
引擎据此算出**数据覆盖率**；覆盖率 < 40% 时，
连**分数和等级一起作废**，显示「数据不足 · 无法评估」并**拒绝给出仓位建议**。

只改建议文案是不够的 —— 用户第一眼看的是那个绿色大数字，
它会直接盖过下面「数据不足」的提示。

**这个原则贯彻到了 provider 层**：RPC 读失败时返回 `contract: null`
而不是空对象 `{}`。返回 `{}` 会让「权限状态未知」冒充「已检查」，把覆盖率从 0% 抬到 30%。

### 6. 部署者 ≠ fee payer（三级来源，实测三个地址互不相同）

用 fee payer 当 creator 会追错人，整个「开发者历史」维度都是错的。
所以 creator 按**三级来源**解析（`src/providers/creator.ts`），从最权威往下回退：

| 优先级 | 来源 | 为什么可信 / 不可信 |
|---|---|---|
| 1 | pump.fun bonding curve 账户第 `49..81` 字节（**程序状态里的 creator**） | 程序自己写的字段、creator fee 的收款方，`set_creator` 可事后改写 —— 最权威 |
| 2 | 链上 Metaplex metadata 的 `creators[0]` | 非 pump.fun 平台常见；**pump.fun 代币实测为空**（链上账户与 DAS 都为空），所以基本只在别的平台生效 |
| 3 | 创建交易的付款方 | **推断值**。它只是付手续费的钱包；打包器/launchpad 发币时它是打包器，不是 dev |

实测 `9raUVuze…pump` 上这三个来源给出**三个不同地址**：

| 地址 | 出处 | 链上事实 |
|---|---|---|
| `Fpi4NERk…` | curve 程序状态（报告采用） | 程序记录的 creator；其**首笔交易资金来自下面那个付款方** |
| `4JBz4tAK…` | 创建交易付款方（＝ launch wallet） | 创建指令的 `user`、签名者；持有 0.37% 代币与**10.8% 的全池 LP** |
| `TSLvdd1p…` | RugCheck `report.creator` / `knownAccounts.CREATOR` | 创建指令的 `accounts[1]`；代币 mint authority 现为 `null`，它不在 metadata、也不持有 LP |

偏移不是猜的：拿一个刚创建、还没被动过的代币（`55VGVACf…`，`complete=0`）对照，
它的 curve 第 `49..81` 字节与创建交易付款方**完全一致**；`9raUVuze…` 上不一致，
说明该币的 creator 在创建后被改过（打包器发币 → 把 creator 转给真 dev）。

因此报告会做到：
- 开发者维度一律按解析出的 `creator` 计算，`creatorSource` 与 `launchWallet` 都进 metrics；
- 两级来源不一致时出结论 + 告警，明说「付费发币的钱包不一定是 dev」，**不猜谁是真的**；
- 只有回退到第 3 级时才把身份标成**推断值**（medium），提醒读者给 dev 结论折价；
- RugCheck 的 `CREATOR` 标签不再用于任何金额计算 —— 实测它指向的是另一个账户。

⚠️ 与 LP 的关系：`creatorLpPct` 现在按**解析后的 creator** 重算。
`9raUVuze…pump` 就因此暴露出一条原先被漏掉的敞口：creator 本人持有 0%，
但**创建钱包持有全池 LP 的 10.8%（占流通部分 29.1%）** —— 只按 RugCheck 的标签算会得到「项目方持有 0」，
把真实的可撤敞口读成没有。

### 7. 「买盘一边倒」可能是蜜罐，不是利好

看到买盘占 97% 容易以为是强势。但若**卖单笔数**极少（< 5%），
真实含义是「根本卖不出去」。所以必须**同时**看金额占比和笔数占比 —— 只看金额会漏报。
反过来只看笔数也会误判：毕业瞬间的抢购笔数极高，并非刷量。

### 8. 刷量要用「净 SOL 流入」而非「笔数」

高笔数 + 净流入 ≈ 0 才是对倒刷量。
进一步地，**笔数比与金额比背离**（买单笔数是卖单 2 倍，但买入金额不到卖出的一半）
说明「小额买盘撑笔数、大额卖盘出货」。

**光有两个比例，读者没法核对**。所以这条结论必须附带逐笔量级证据
（`liquidity.tradeSizeAudit`，来自最近 100 笔中能判定方向的成交）：

```
[high] 笔数与金额背离
  买单笔数是卖单 4.2 倍，但买入金额只有卖出的 78%。小额买盘撑笔数、大额卖盘出货。
  样本：最近 78 笔可判定方向的成交，跨约 65.5 小时。
  买单 63 笔共 1.810 SOL（平均 0.0287、中位 0.0025），
  卖单 15 笔共 2.311 SOL（平均 0.1541、中位 0.0113，平均是买单的 5.4 倍）。
  最大单笔卖单 2.028 SOL，占卖出总额 87.7%；前 5 大卖单合计占 96.4%。
```

四个数字缺一不可，各自反驳一种误读：

| 数字 | 反驳的误读 |
|---|---|
| 样本笔数与**时间跨度** | 「100 笔」可能只是几分钟的机器人噪声，也可能是几天 —— 不说清就没法判断代表性 |
| 单笔**中位数** | 平均值会被大单拉高；中位数才能说明「绝大多数买单有多小」 |
| 平均卖单 / 平均买单 | 把「笔数多」和「金额大」拆开：这个倍数才是「大额卖盘」的直接度量 |
| 最大单笔卖单占比 + 前 5 大卖单占比 | 说明卖压是否集中在极少数几笔 —— 一笔就占 87.7%，和几十笔均匀卖出完全是两回事 |

只有单边成交时**不给**这些数字：那时中位数会算成 0，会被读成「卖单很小」，
而真相是「没有卖单」。USD 口径同理不换算单笔量级（受价格波动影响）。

### 8.1 每个数字都要能点到链上核对

`最大单笔卖单 2.028 SOL，占卖出总额 87.7%` 仍然只是一个需要读者相信的数字。
所以最大的几笔卖单会带上**交易签名、时间、卖出钱包**，UI 里签名直接链到 Solscan
（`dimensions.liquidity.metrics.largeSells`）：

```
[high] 笔数与金额背离
  …最大单笔卖单 2.028 SOL，占卖出总额 87.7%；前 5 大卖单合计占 96.4%。
  最大 5 笔卖单（签名可在 Solscan 核对，完整明细见下方「大额卖单明细」）：
  2.028 SOL @ 10-11 00:26 UTC，钱包 Cttj…2nou，签名 4JBM1K…uEfYXZ；
  0.108 SOL @ 10-08 17:46 UTC，钱包 76Y1…w8FT，签名 3tSPLq…MqLkei；
  0.037 SOL @ 10-11 01:30 UTC，钱包 BzQB…2bkN，签名 5qWZim…ShanAf。
```

用 `getTransaction` 复核上面第一笔的实测结果 —— 报告的每个数都对得上：

| 报告里写的 | 链上读到的 |
|---|---|
| 时间 `10-11 00:26 UTC` | `blockTime 2026-10-11T00:26:49Z` |
| 卖出钱包 `Cttj…2nou` | `fee payer = CttjirRWSL19HuMJMBcb7RVs49Tf4AaNnEXw6vjH2nou` |
| 金额 `2.028 SOL` | `postBalances − preBalances = +2.027926167 SOL`（收到 SOL＝卖出） |

金额为 0 或没有签名的条目不进这份明细：无法核对的东西不进报告。
只有一笔大额卖单时也照列 —— 这恰恰是最需要看的情况。

### 8.2 光有金额还不够：砸盘的是**开盘那批人**吗

同样是「一笔 2 SOL 砸下来」，开盘就买入的狙击手在出货，与半路进场的持有人止盈，
性质完全不同。所以每一笔大额卖单都会标注身份（`largeSells[].earlyBuyerIndex` / `isCreator`）：

| 身份列 | 含义 |
|---|---|
| 部署者 | 该钱包就是 creator |
| 开盘第 N 笔买入 | 该钱包在代币**最早 25 笔成交**之内（狙击窗口） |
| 不在最早 25 笔内 | 不是最早 25 笔成交的付款方 |
| 身份未知（没取到最早成交） | 这次没取到最早成交，**不能**读成「不是狙击手」 |
| 当前持仓 | 该钱包现在还在不在前 20 大持仓里（砸完就走的与砸完还留着的含义不同） |

⚠️ 第三行与第四行必须分开：把「没查到」渲染成「不在最早 25 笔内」，
等于把未知说成清白。窗口不可用时 `earlyBuyerWindowKnown = false`，UI 与结论都会换成未知口径。

实测 `9raUVuze…pump`：最大的 5 笔卖单**没有一笔**来自开盘最早 25 笔成交内的地址，
且这些地址都已不在前 20 大持仓里 —— 也就是说，这次砸盘的不是开盘那批狙击手。


### 9. 权限必须读到 `null` 才算「已放弃」

`c.mintAuthority ? 0 : 1` 会把 `undefined`（没读到）当成「已放弃」，
在 UI 上渲染成绿色的安全标记。所以权限状态是**三态**：
`1` = 已放弃，`0` = 未放弃，`-1` = 未知。

### 10. 代币程序必须读 `getAccountInfo().owner`

`getParsedAccountInfo` 返回的 `parsed.info.owner` 是 **authority**，不是代币程序。
混淆这两者会导致「所有代币都用了 Token-2022」的严重误判。

### 11. dev 卖出部分 ≠ rug；账号新 ≠ bot

部分回收成本在 meme 圈极常见，只有「清仓 + 时间很早」才升级为高危。
同理，meme 玩家本来就开新钱包新 X 号，判定 bot 要看**行为聚类**而不是注册时间。

### 12. 不猜

拿不到的字段留空。「这个代币是不是 rug」需要价格与流动性历史，
单次 RPC 查询无法负责任地断言 —— 因此 `priorRugCount` **不猜**，
宁可留空也不用启发式编一个看起来确定的数字。

### 13. 声明了却没有任何 provider 写入的字段 = 死分支

比「猜」更隐蔽的一类错误：**schema 里有字段、分析器里消费了它，但没有一个
provider 会写它**。于是分支永远走同一条，结论永远同一种，而代码看起来
「检查过了」。

真实案例：`contract.lp.locked / burned` 与 `liquidity.lpLockedOrBurned`
从来没有任何数据源写入。后果是三重的：

1. **「LP 已销毁 / 已锁定」这两条好事永远不可能出现**（死代码）；
2. 每个有池的代币都固定背一条 high 风险「LP 锁定状态未知」，
   而真正的风险（LP 由单一地址持有、随时可撤）根本没被识别；
3. 同一事实在 `contract.ts` 与 `liquidity.ts` 各判一次，**重复扣分**。

修法是二选一，绝不允许「留着好看」：接真实数据源把它填上（现在由 RugCheck
提供 LP 比例与 LP 持有者），或者删掉字段与分支。同批清理的还有
`liquidityPulled` / `pulledLiquidity`（抽池没有前后快照可判）、
`fundedByMixer` / `hopCount`（跳数接口已下线）、`isTeamWallet`（没有资金图谱）、
`virtualSolReserves` / `graduationTargetSol` / `holderGrowth24h`（无来源），
以及 `priorTokens[].rugged`（要么真去回溯历史，要么别声称「记录干净」）。

**判据**：一个字段若只出现在 `types.ts`、分析器和 fixtures 里，
却从没出现在 `providers/` 的赋值语句右边 —— 它就是死字段。
对应的测试也补上了：`引擎测试 §9` 专门锁「字段没人写 ≠ 字段是 false」。

### 14. 「有账户」不等于「是钱包」—— 看 owner 程序，别看到账户就放行

判断一个持仓是个人还是程序托管，唯一可靠的判据是**账户的 owner 程序**：

| owner 程序 | 含义 |
| --- | --- |
| System Program (`1111…`) | 普通钱包 |
| Jupiter Lock | 时间锁仓（可读出解锁时间） |
| Squads 等 | 多签金库（**不剔除**） |
| AMM / 联合曲线 | 池子储备金库（按流动性剔除） |
| 查不到账户（PDA） | 回退：用 token account 创建交易反查 |

**踩过的坑**：旧代码把「owner 有账户」直接当成「普通钱包」而跳过。
但 Jupiter Lock 的 `VestingEscrow` **本身就是一个有数据的账户**（296 字节），
owner 正是 Lock 程序。结果 `9raUVuzeWUk…pump` 上那个占 **72% 供应量**的
锁仓仓位被当成普通巨鲸，报告给出「持仓集中度过高」的硬否决 —— 完全错误的结论。
修正后同一代币：否决消失，集中度从「过高」变为 **Top10 仅 8.2%**。

同理，池子也不该靠地址文本猜：用 **AMM 程序 id** 判定其拥有的账户是储备金库，
比正则可靠得多（实测某代币的 PumpSwap 金库占 5.15%，旧的池识别完全没认出来）。

### 15.5 「锁定比例」既不是「能不能撤走」，也不是「锁定」—— 它是**已销毁**

RugCheck 的 `lpLockedPct` 名字叫「锁定」，但它实际是**不在流通中的 LP 比例**：
`lpTotalSupply`（历史铸造总量）− 当前流通量。到底是不是销毁，必须用链上读数核对，
而不能按字段名读。实测（`getParsedAccountInfo` 读 LP mint 的 `supply`）：

| 代币 | RugCheck 说 | 链上 LP mint 供应量 | 真相 |
|---|---|---|---|
| `9iryaLJ…pump` | 锁定 100% | 0（铸过 4,193,388,354,147） | 全部**已销毁** |
| `9raUVuze…pump` | 锁定 62.86% | 2,477,306,894,096（铸过 6,670,716,023,992） | 4,193,409,129,896 **已销毁**，其余 37.14% 在新铸的持有人手里 |

`9raUVuze…pump` 是按字面读会出错的最好例子：pump.fun 迁移确实销毁了 LP
（约 4.19e12，每个毕业生都接近这个数），但在那之后任何人都能往池子里加流动性，
池子会**新铸** LP 给添加者。于是「锁定 62.9%」既不是「未锁定也未销毁」，
也不是「项目方随时可以撤池」—— 它意味着：

- 62.9% 的流动性凭证已永久销毁，无法撤池（**好事**，且比「锁定」更硬）；
- 剩下的 37.1% 是新铸的流通 LP，分散在 20 个地址（最大一个占流通量的 33.3%），
  这些是各自加池子的持有人，撤走自己那份是正常的 AMM 行为，不是跑路。

所以 LP 结论由四个**各自独立测量**的数字支撑，缺哪个就少说哪句：

| 数字 | 来源 | 说明什么 |
|---|---|---|
| `burnedPct` | 链上 LP mint：`历史铸造量 − 当前供应量` | 真正已销毁的比例（不可逆） |
| `lockerPct` | 链上 LP mint 持有者 ∩ 锁仓程序账户 | 锁仓/线性解锁合约托管了多少，附解锁时间 |
| `withdrawablePct` | 链上 LP mint 持有者中的**普通钱包** | 仍在流通、可随时提走的敞口 |
| `topCirculatingHolderPct` / `creatorLpPct` | 流通部分按持有人细分 | 是第三方各自加池子，还是项目方自己攥着 |
| `lpAllHolders` + `creator`/`launchWallet` | 解析后的部署者地址 ∩ LP 持有者全量（≤20） | **与部署者关联的钱包**持有多少可撤敞口 |

「关联钱包」＝解析出的 creator、创建交易付款方、以及给 creator 首笔交易出资的钱包。
门槛卡在**占全池 LP 的比例**（≥5% 报 medium、≥50% 报 high），不是占流通量的比例 ——
后者会把「销毁 96% 的池子里有人拿着剩下那 4%」放大成警报，而它实际只能抽走池子的 3%。


判定顺序：整体销毁（≥95%）→ 报「LP 已销毁」；部分销毁 → 先报已销毁的比例与
原始数字，再看流通部分：项目方持有（≥5% 流通量）报 high，单一地址占流通量 ≥50%
报 medium，≥3 个地址分散持有报 low，只有 1–2 个地址且占比不小报 medium。
**比例之间不做加减法凑账**：`lpUnlocked` 与 `holders[]` 并不总自洽
（`BdzaE3T7…pump` 的明细合计 50.9%，与锁定比例推算的 49.4% 差 1.5%），
差超过 1 个百分点就在结论里写明「两个口径对不上，差额不做推断」。
拿不到持有者明细时只报「流通中的 LP 持有人无法核实」（medium），
不编风险、也不当成安全。

### 16. 锁仓要剔除，但**多签不能剔除**，且剔除后必须列出来

「巨鲸 / 集中度」只应统计**能随时卖出**的筹码，所以时间锁仓必须剔除。
但这里有两个坑：

**坑一：多签不是锁仓。** Squads 这类多签金库可以随时凑齐签名转出，
把它当锁仓剔除 ＝ 把真巨鲸放过去，是危险的漏报。
因此 `EXCLUDED_HOLDER_KINDS` 只含 `pool / burn / timelock`，
`custody`（多签、未确认托管）**照常计入集中度**，只是单独标注。

**坑二：剔除不能变成「看不见」。** 被剔除的锁仓会单独列成一张表，
显示占比、控制程序和**解锁时间**，并明写「是否计入集中度」，
避免「悄悄扣掉一笔」变成隐性漏报。

判定方式（全部来自链上，不猜）：token account 的 authority 不是普通钱包
而是某个程序的 PDA —— 普通钱包一定有账户，PDA 没有账户；
再用该 token account **最早一笔交易里的 program id** 确认是哪个程序。

**只认已核实名单里的程序。** 早期版本把「交易里第一个非系统程序」当作
控制方，结果把某 pump.fun 代币的 5 个持仓标成「托管程序 DF1ow4…」，
而 `DF1ow4…` 实为 `SOLANA_PROGRAM_LIBRARY`（程序库），根本不是托管方。
**名字猜错比不标更糟**，所以名单外的程序一律不标注、不剔除。

**优先级：链上确认的事实 > 文本启发式。** 池标签只是拿地址字符串正则碰运气，
`custody` 是链上反查出来的确证事实。曾经把正则排在前面，
结果地址里带 `vault` 的已确认锁仓仓位被误判成池并静默剔除 ——
既没列出、也没算进集中度。

**解锁时间**：Jupiter Lock 的 `VestingEscrow` 布局已对着真实账户反推并交叉验证，
现在能给出**首次解锁**与**全部解锁**两个日期（例如实测某代币为
2026-10-01 → 2032-07-01，720,000,000 枚按月线性释放）。
三条独立校验支撑该偏移：

1. 托管账户 `[40:72]` 解出的 base58 **正好等于**它对应的 mint
2. `cliff_time − vesting_start_time` **正好等于 1 个 `frequency`**（30 天）
3. `cliff 额度 + 每期额度 × 期数` = **正好等于该账户实际持有的代币数量**

时间戳不合理（越界或全零）时**返回 null**，如实显示「待接入」，
绝不编一个日期出来。其它锁仓程序（Streamflow 等）尚未接入，同样标「待接入」。

### 17. 全量持有人总览：三个口径要同时摆出来，明细不能一次塞给浏览器

前 20 名回答不了「筹码结构长什么样」。`getProgramAccounts` 可以一次拿到该 mint 的
**全部** token account —— 实测 `9raUVuze…pump` 的 9,447 个账户，一次调用 **642ms**：

```ts
// token account 布局：mint@0(32) owner@32(32) amount@64(8)
// 切片 32..72 正好同时覆盖 owner 与余额，两个代币程序（经典/Token-2022）布局一致
{ filters: [{ dataSize: 165 }, { memcmp: { offset: 0, bytes: mint } }],
  dataSlice: { offset: 32, length: 40 } }
```

**「持有人数」在这个币上有三个答案，必须同时说清楚：**

| 口径 | 数值 | 说明 |
|---|---|---|
| 链上 token account | 9,447 | 含卖光后没关闭的空账户 |
| 其中有余额 | 5,566 | 3,881 个是空账户（41%） |
| RugCheck `totalHolders` | 9,456 | 第三方口径，与上面两个都对不上 |

差额不做推断，报告在 warnings 里把三个数一起列出来。

**关于「按 owner 合并」**：同一个地址可能有多个 token account（实测有 owner 拿 3 个），
按账户数当持有人会把一个人算成几个。总览按 **owner 合并**（5,558 个有余额持有人），
同时把账户数一起显示。

**同一个 Top10 会算出三个数 —— 因为分母不同，所以三个都要给：**

| 口径 | Top10 | 分母 | 用途 |
|---|---|---|---|
| 含池 / 销毁 / 锁仓 | 84.68% | 总供应量 | 看着最吓人，但那 72% 锁仓卖不掉 |
| 剔除后 | 8.20% | 总供应量 | 报告里 Top10 集中度的**分子**，也是表格「计入」行的合计 |
| 剔除后 | 38.22% | 流通盘（总量 − 剔除项） | 报告里 Top10 集中度的**最终数值**（8.20 ÷ 21.45），与 finding 完全一致 |

只画一条曲线，读者会以为这一页和上面的集中度自相矛盾；只给两个数，也解释不了第三个。
界面上三条都列出，并写明「同一个数、不同分母」。

**为什么明细要按需加载**：全量是几千到几万行。扫描时只自动算**聚合**
（分桶 + 曲线 + 标量，几百字节），逐行明细走 `/api/holders`
分页取（服务端切片、搜索、分类筛选、CSV 导出），页面默认一行都不渲染。
账户数超过 `THRESHOLDS.holders.overviewMaxAccounts`（2 万）时连聚合也不自动拉 ——
改成按钮，理由是实测 9.4k 账户 642ms / 2.2MB，再大就会明显拖慢扫描并放大失败面。
点按钮会带 `forceOverview` 重新扫描一次（用户明确要求了，慢也要拉）。

**降级与不完整的处理**：RPC 全量枚举失败（被拒 / 限流）时自动降级为
Helius DAS `getTokenAccounts` 分页（1000/页 ≈ 1s），并在 `overview.source` /
`truncated` 上如实标注「分页兜底」「未取全」，界面显示 ⚠️。
明细接口的缓存过期（10 分钟）后返回 409 + 「请先扫描一次」，
**不拿旧数据假装是新的**。


### 18. 「占流通盘」不能拿「占总供应量」的数冒充 —— 一次真实的漏报

**修之前**：`top10Pct` 的分子分母都是「占总供应量」，但 finding 写成「占流通盘」，
阈值注释也写着「Top10 占流通盘 > 25% 警惕」。锁仓/大池的代币流通盘很薄，两个口径能差几倍：

| 指标（`9raUVuze…pump`） | 值 |
|---|---|
| 前 10 名持仓（占总供应量） | 8.20% |
| 池 + burn + 锁仓 | 78.55% |
| 真实流通盘 | 21.45% |
| **前 10 名占流通盘** | **38.22%** |

于是报告一边说「真实流通盘 21.9%」，一边说「持仓分布健康：前 10 大持有者仅占流通盘 8.2%」，
而实际上这 10 个地址握着流通盘的 **38.2%**，早就越过 25% 警戒线 ——
**这是漏报**，而且锁仓越大误差越大。

**修之后**：

- 分子 = 全量枚举里剔除后前 10 名（占总供应量），分母 = 流通盘（＝100 − 池/销毁/锁仓）
- 分子分母**同源**：都优先取全量枚举（`metrics.top10Source === 'full'`），
  没有全量时回退前 20 名样本并标注 `'sample'`（那个币两种算法一致：8.1997% vs 8.20%）
- 分母用 `100 − 剔除项` 而不是「枚举到的计入项之和」：后者在枚举不完整时会把
  分母算小、集中度算得虚高
- **同一 bug 类别的判定全部换成同一个分母**（用 `ofCirculating()` 一个换算入口）：
  「单一巨鲸」（10%）、「dev 持仓偏高」（15%）、「狙击钱包筹码偏多」（25%）、
  「程序托管」的尘埃门槛（1%）。否则同一份报告里 Top10 用流通盘、dev 用总量，
  读者会以为这两个数能相加。每个文案都把两个口径都写出来：
  「持有流通盘的 12.9%（2.8% 的总供应量，流通盘 21.5%）」，可以逐行对账
- 全量持有人总览的曲线第三列用**同一个分母**，所以界面上那个 38.22% 和
  finding 里的 38.22% 保证是同一个数（有测试锁住）

结果：该币 findings 从「持仓分布健康」变成「Top10 持仓偏集中（38.2% > 25%）」
＋「存在单一巨鲸（流通盘 12.9%）」，总分 27.9 → 34.9。
**这是把漏报补上，不是把标准调严** —— 阈值的注释（「占流通盘 > 25% 警惕」）
本来就是这么写的，之前是喂错了分母。

⚠️ 副作用要知情：锁仓/销毁比例很高的代币流通盘很薄，换算后集中度类指标普遍上升，
以前「健康」的币现在可能报 medium。这是真实风险，不是噪声 ——
但如果你觉得阈值本身也该跟着调（比如 25% 是按总量口径定的），那是另一件事，需要单独定。


### 19. 钻石手：一个**权重为 0** 的维度，因为它描述的不是风险方向

用户要求加「钻石手」维度。做法上最关键的决定是：**它不参与总分**（`WEIGHTS.diamond = 0`）。

理由不是「不重要」，而是**方向不能反**：

- 这个维度分数高＝筹码拿得住（抛压小），听着像利好；
- 但 pump.fun 上一个刚发 10 分钟的新币，**没有任何人卖过** ——
  按「拿得住」评分，它会系统性地排在最前面。这就把「还没到卖出阶段」包装成了优点。
- 所以它只回答「筹码在谁手里、拿了多久」，不回答「该不该买」，也不否决。

同理，它**刻意不画进雷达图**：雷达图是「越鼓越危险」，把方向相反的一维画进去，
会被读成「钻石手越多越危险」。

**三个信号**（全部来自**逐地址**成交，不是聚合数字）：

| 信号 | 判定 | 为什么这样定 |
|---|---|---|
| 买了不卖 | 窗口内只有买入、无卖出 | 有卖出记录就直接排除，不做「卖了一部分」的模糊判断 |
| 仍持仓 | 当前余额 > 0（**全量枚举**交叉验证） | 卖了又买回来的、余额归零的，都不算 |
| 拿得住 | 首次买入至今 ≥ 7 天 | 刚买的人当然没卖，不给最短期限会让新币全部命中 |
| 还在加仓 | 窗口内买入 ≥ 2 次 | 一把梭 ≠ 持续看好，分开标 |

**三条必须写进结论的边界：**

1. **「没看到卖」≠「没卖过」** —— 成交窗口只取了最近 100 笔 + 最早 25 笔，
   中间的历史没拉。实测 `9raUVuze…pump`：窗口只覆盖 **9%** 的时间跨度
   （中间缺 677 天）。所以报告里有一条 finding 专门说这件事，并写明
   「比例**几乎肯定低估**」；覆盖率低于 `minWindowCoveragePct` 时，
   连「筹码在长期持有者手里」这条描述都不给。
2. **证据强度分级** —— 只有落在**最早**窗口内的钱包，「至今未卖」才覆盖最长的时间跨度；
   最近窗口里刚买进的钱包没卖是因为刚买（`inEarlyWindow: false`，界面标「窗口内新进」）。
3. **要排除两类地址** —— creator/关联钱包（部署者自己没卖不是社区行为）、
   高频买卖交替 ≥ 12 次的地址（机器人/做市，既不是钻石手也不是散户）。
   两类都在结论里写明排除了几个，不静默丢弃。

**「没数据」不等于「0 个钻石手」**：拿不到逐地址成交时，`metrics.available = 0`、
维度分数不计入覆盖率，finding 写「持仓行为无法分析……这不是「没有钻石手」，是这一项没数据」。
这和项目里其它地方的处理一致（未知 ≠ 安全 ≠ 危险）。

**实测**（`9raUVuze…pump`）：53 个可分析钱包里 3 个是钻石手（占 5.7%），
中位持有 688 天，全部落在最早窗口内，都是只买过一次的小额买入（0.05–0.11 SOL）。

**未做的部分**：真实的「买入价 vs 现价」盈亏需要逐地址拉完整历史
（实测单地址 ~2.1s，前 50 名就是 50 次请求 / ~2 分钟），当前不做；
所以这个维度只能给「买了没卖」，不能给「赚了还是亏了」。


### 20. 抛压分布：先修一个会算出「浮盈 +54771%」的坑

「抛压分布」回答的是：这些**还没卖**的筹码在什么价位、还有多少、谁拿着。
核心是**成本价** —— 用「该地址的 SOL 净变化 ÷ 它的代币净变化」反推每笔成交单价，
再按代币量加权平均。

**第一个坑（实测踩到了）**：`CREATE`/`TOKEN_MINT` 交易绝不能用这个公式。

```
2024-09-27 pump.fun CREATE 交易：
  铸造 10 亿枚 → bonding curve
  转 357,547 枚 → 创建者
  创建者 SOL 净变化：-0.036 SOL（只是网络手续费）
  → 按公式算出的「成本」= 0.036 / 357547 = 1.02e-7 SOL/枚
  → 对照现价 2.3e-5，报告出「浮盈 +54771%」
```

这些筹码是**凭空得的，没有买入价**。现在把它们单独记账（`mintedWallets` /
`mintedUnsoldTokens`），不进成本加权、不进盈亏分桶，并在报告里说明
「这类筹码在任何价位卖出都是纯利润，只能用占比衡量」。

**第二个坑**：配对率的**分母**。第一版写成 `paired / sp.trades.length`，
而 `sp.trades` 本身已经过滤过 → 永远 100% → 「只覆盖一小部分筹码」这条最关键的
警告永远不会出现。现在分母是 `windowTrades`（窗口内全部成交），实测 42/103 ≈ 41%。

**「抛压」的定义**（三者缺一就会被误读）：

| 规则 | 做法 | 为什么 |
|---|---|---|
| 已卖光的排出 | 卖出 ≥90% 的进「已出走」，不构成抛压 | 赚了 20 倍但已经跑了的筹码不会再来砸盘 |
| 派发中的折算 | 卖 30%–90% 的只按剩余部分计入 | 「抛压」指的是**还没砸出来的量** |
| 未卖量取下界 | 窗口估算 vs 全量余额取较小值 | 窗口没覆盖的卖出看不到，估算会**高估**剩余量 |

**现价是反推的**：取窗口内最近一笔可配对成交的单价，超过 24 小时就停用盈亏一栏
（实测该币最近成交距扫描时 16322 小时，那个价格早已不代表现价），
那时改给「按成本价区间」的分布 —— 仍然能回答「筹码集中在高位还是低位」。
盈亏分桶按**行为心理**定边界（回本区 -10%~+10% 最容易触发卖出；深亏 >50% 通常死拿），
不按等距。

**实测**（`9raUVuze…pump`）：可分析 14 个钱包、配对率 98.3%，未卖筹码合计
1.0% 流通盘 / 成本 1.46 SOL；8 个钱包处于浮盈 >200%（合计 1.0% 流通盘），
1 个是铸造获得的 35.7 万枚（无买入价）。

### 20.1 深度模式：把「窗口估算」换成「真实成本」

窗口口径有个硬伤：实测只覆盖 9% 的时间跨度，于是抛压分布只能算出 14 个钱包、
未卖筹码算出来是 1.0% 流通盘 —— **严重低估**。

深度模式对前 50 名持有人**逐地址拉完整历史**（`src/providers/deepHolders.ts`），
效果（同一代币实测）：

| | 窗口口径 | 深度模式 |
|---|---|---|
| 可分析钱包 | 14 | **43** |
| 未卖筹码 | 1.0% 流通盘 | **12.4%** |
| 成本来源 | 窗口估算 | 其中 39 个是**完整历史** |
| 已卖比例 | 只能看到窗口内的 | 完整、可信 |

**代价与工程约束**（都是实测数字，不是估算）：

- **约 2 分钟**：50 个地址、11,685 笔历史、133 次分页请求。所以做成
  「启动任务 → 轮询进度 → 完成后自动重扫」，而不是一个同步请求
  （38 秒以上的同步请求在浏览器/代理/Serverless 三处都会超时，且失败时用户看不到进度）。
- **并发只能是 3**：并发 8 时 50 个请求里 **45 个被 429 拒掉**；并发 3 + 指数退避
  才 50/50 成功。这是硬约束，不是可调参数。
- **结果缓存 15 分钟**：2 分钟的活不重复干；缓存命中时按钮显示「重新深度分析」。
- **缓存丢失要说清楚**：任务表在内存里，服务重启会清空 —— 那时接口返回
  「任务不存在或已过期，请重新发起」，而不是假装还在跑。

**可信度分级是显式的**：表里逐行标注「完整历史 / 窗口估算」——
深度数据只覆盖前 50 名，其余地址仍是窗口估算，两者混在一张表里
**必须**让人分得清，否则「窗口估算」会被当成「真实成本」。

**为什么是 50 名而不是 200 名**（实测，推翻了我自己一开始的猜测）：

| 覆盖范围 | 占全部持仓筹码 | 增量 |
|---|---|---|
| 前 50 名 | **91.2%** | — |
| 前 200 名 | 95.4% | +4.2pp |
| 前 500 名 | 97.5% | +2.1pp（500 个地址只为 2.1pp） |

我原本以为长尾可能不小，实测证明**头部已经足够**：meme 币的持仓分布极度头部化，
前 50 名就代表 91% 的筹码；再多拉 150 个地址只能多 4.2 个百分点，
而且分散在 150 个钱包里、每个的抛压都很小。所以固定在 50 名。

**串行队列**（`deepJobs.ts`）：同一时间**只跑一个**深度任务，其余排队。

这不是为了省资源，是因为**限流会静默丢数据**：实测并发 8 时 50 个请求里
45 个被 429 拒掉，那些地址会悄悄退回窗口估算 —— 用户看到一个「看起来完成了、
其实缺了一半」的结果。「慢一点」是可接受的，「错一点」不是。
排队中的任务会带位置与预计等待时间（实测预估 120s、实际 126s，误差可接受），
界面显示「前面有 N 个任务 / 预计等待 X 分钟」，而不是一个干等的 0% 进度条。

⚠️ 队列**只服务用户主动发起**的深度分析，没有任何自动预热 ——
等待必须是用户自己按下去的，不能被系统偷偷占用配额。

**过程中又修了两个 bug**：

1. **现价取错数据源**：`impliedPrice` 用的是原始窗口成交，没走合并后的数据。
   深度数据里往往有更新的成交，忽略它们会拿到陈旧价格 —— 实测把现价算错 10 倍，
   进而**把浮亏的钱包报成浮盈**。现在从合并后的成交反推。
2. **配对率超过 100%**：深度模式下分子含完整历史成交、分母仍是窗口笔数，
   实测报出 **3344%**。而且更早还有一层错：`windowTrades` 用的是「已配对的笔数」，
   导致这个比例恒为 100%、最关键的警告永不出现。现在 provider 层把
   **配对失败的笔数**（`unattributedTrades`）单独计数传下来，分母是窗口内全部成交，
   实测真实配对率 **57.3%**；深度模式下这个比例不再给（分子分母不同源，给了就是错的），
   改用「深度覆盖地址数」表达完整度。



### 21. 报告分页：把 9 个区块收进 5 个 tab

报告越加越长（9 个区块，含两张可分页的大表和一个 2 分钟的深度分析入口），
平铺成一页要滚很久，「找抛压」得在十几屏里翻。分成 5 个 tab：

| tab | 内容 |
|---|---|
| 概览（默认） | 雷达图 + 各维度得分 → 逐项体检明细 → 数据来源与局限 |
| 持仓 | 持币集中度方程、全量持有人总览、集中度曲线、Top20 表、全量持币人明细 |
| 资金流 | 大额卖单明细 |
| 持仓行为 | 钻石手、抛压分布（含深度分析入口） |

**why 4 而不是 5**：「数据来源」原本是独立 tab，但它只有约 3,800 字、
没有任何交互 —— 单独占一个 tab 的代价（多一次点击、多一层导航）大于收益，
故并入概览。概览的顺序是刻意的：**先分数（一眼看风险）→ 再明细 → 最后来源**，
中间有一条「以下是每个维度的依据」分隔线，避免读者把依据当成又一份结论。

**⚠️ 分 tab 时踩过的坑：复制而不是移动。**
第一次拆分时，概览 tab 里遗留了一整份所有区块的副本（Custody、总览、Top20、
全量明细、大额卖单、钻石手、抛压、来源），本意是「移过去」结果变成了「复制一份」——
同一个区块在页面上渲染两次。现在有测试锁住「每个区块全局只能出现一次」。

**另一处真重复：概览的「六维速览」与明细的「逐项体检明细」。**
两者显示同一批数字（Top10 38.22%、净流入 −0.5、卖单额 56.07%…），
只是一份精简、一份完整。两份数字将来会各自漂移 —— 改口径只改一处，
用户就会看到两个互相矛盾的值。现在**概览只给各维度得分**（371 字 → 192 字），
细节数字只存在于「逐项体检明细」，概览里放一个跳转链接。

**两条不能妥协的约定**（`reportTabs.ts` + 测试锁住）：

1. **结论与硬否决不属于任何 tab** —— 它们是常驻头部。
   硬否决是「一票判死」的结论，如果藏在默认不可见的页里等于没显示；
   建议仓位是用户最需要一眼看到的数字。测试里 `ALWAYS_VISIBLE` 单独声明这两项，
   并检查它们**没有**同时出现在任何 tab 的区块列表里（否则会重复渲染）。
2. **区块必须有归属** —— 测试列出一份「既有区块清单」，
   新增区块时如果没决定放哪个 tab，测试会失败。
   这是防止「加了个区块但忘了放进页面」这类静默丢失。

**用 `hidden` 而不是条件渲染**：切回某个 tab 时，用户已输入的搜索词、
翻到的页码、展开的详情都会保留。实测：在持仓 tab 的搜索框输入地址 →
切到概览 → 切回持仓，输入框的值仍在，不需要重新输入。

**隐藏面板不会偷偷发请求**：实测切到「持仓」tab 时没有新增任何请求 ——
全量持币人明细仍然要用户主动点开才加载，分页只在需要时拉。
（如果用条件渲染，每次切 tab 都会重新挂载组件、重新请求一遍。）


### 22. 阈值重校准：实测发现「不是阈值该调，是口径在小样本上失真」

改分母（总供应 → 流通盘）之后，那几个按旧口径拍的阈值
（Top10 25/40、dev cluster 15、sniper 25、单鲸 10）就可能失效。
为了用数据决定改哪些数，批量扫了 **44 个真实代币**（30 个新币 + 14 个已毕业的成熟币），
同时记录新旧两种口径。

**结果推翻了我的预设 —— 阈值本身没问题，问题在分母。**

按持有人数分组，看 Top10 集中度（中位数）：

| 持有人数 | n | 占流通盘（新） | 占总供应（旧） | 两者差距 |
|---|---|---|---|---|
| < 20 | 14 | **100.0%** | 51.1% | +48.9pp |
| 20–100 | 7 | 90.8% | 31.0% | +32.1pp |
| 100–1000 | 9 | 48.3% | 22.9% | +21.6pp |
| 1000–10000 | 10 | 21.1% | 18.3% | **+1.9pp** |
| > 10000 | 4 | 23.7% | 22.2% | **+1.9pp** |

分界线在 1000 人附近：到那个量级两种口径几乎一致（差 1.9pp），
**说明换分母这件事本身是对的**。但在持有人 < 100 时，剔除池/销毁后的流通盘
本身就很小，几个散户就能占满分母 → 恒等于 100%，这不是「更准确」，
是**在小样本上失真**。

后果很严重：Top10 硬否决的触发率

| 样本 | 旧口径 >40% | 新口径 >40%（修前） |
|---|---|---|
| 成熟币（≥1000 人） | 0/14 | 0/14 |
| 小样本（<100 人） | 12/21 | **20/21** |

成熟币两种口径都不触发，说明阈值 40% 是合理的；而小样本几乎全触发 ——
**多出来的不是风险，是分母失真**。实测 30 个样本里 24 个被这条硬否决误杀。

**修法（`percentageCaliberMinHolders: 1000`）**：持有人数低于下限时
不再输出「占流通盘 X%」并据此判风险，改为按「人数 + 已知类型分布」描述：

> 持有人仅 12 个 —— 百分比口径在此不适用
> 这个代币只有 12 个持币地址（低于 1000 个的统计下限），前 10 名各自的占比已失去统计意义……
> 前 10 名的已知构成：creator 本人 1、散户 9。
> ⚠️ 人少本身就是最大的风险：没有出货深度，任何一笔卖出都可能砸穿价格。

三个必须守住的边界：

1. **人数未知 ≠ 人数不足**。`holderCount === undefined` 时**不套用**这个分支 ——
   拿不到人数不代表人少，套用会白白丢掉一个本来有效的判断。
2. **不是「人少就不算风险」**。「持有人少且集中」这条 finding 仍然保留，
   而且新提示里明确写出「人少本身就是最大的风险」—— 没有出货深度。
3. **修后没有反向漏报**。验证时逐个检查了仍为 100 分的代币，
   它们都是被**另一个真实原因**否决的（「部署者已清仓」），
   且新的口径提示与它并存。

顺带清理了一处重复：持仓分类的显示名原先在 UI 里散着两份
（长名一份、短名一份），分析器再要一份就变成三份。现在统一到
`constants.HOLDER_KIND_LABELS`（同时提供长名/短名），改名字只需改一处。

实测验证（30 个样本重扫）：Top10 硬否决 **24/30 → 0/30**，
28/30 正确触发了口径提示，2 个未触发的是持有人数达标（≥1000）的真币。



### 23. 中英双语：结论不能是「字符串」，得是「结论 ID + 参数」

做多语言时最容易低估的是**分析器里的结论文案**：这个项目的 findings 原本是
硬编码中文模板字符串，约 12,000 字，占全部待翻译文案的 58%。更麻烦的是它们
大量带运行时插值（「前 10 大持有者占流通盘 38.2%，超过 25% 警戒线」），
而中文和英文的数字位置、语序、断句都不一样。

**做法：分析器不再产出「文案」，只产出「结论 ID + 参数」。**

```ts
// 迁移前：文案在分析器里就定死了，英文用户只能看到中文
add('high', 'Top10 持仓过度集中', `前 10 大持有者占流通盘 ${pct}%，超过 ${threshold}% 警戒线。`);

// 迁移后：只给 id 与参数，渲染层按当前语言查字典
add('high', 'holders.top10Danger', 'Top10 持仓过度集中',
    `前 10 大持有者占流通盘 ${pct}%，超过 ${threshold}% 警戒线。`,
    { pct, threshold });
```

`Finding` 因此多了 `id` 与 `params`；`title`/`detail` 作为**过渡期中文回退**保留
（渲染层优先查字典，查不到才用它）。

#### 三个非显然的收益

1. **漏译变成编译错误，而不是页面上少一句话。**
   `Messages = DeepStringify<typeof zh>`，`en.ts` 缺任何一个 key 都编译失败。
   页面少一段话是**最难发现的 bug** —— 用户不会报告「这里应该有句话但没有」。

2. **测试可以断言语义，而不是措辞。**
   原来测试写 `assert.equal(f.title, 'Top10 持仓过度集中')`，改一个字的文案
   就会让逻辑测试失败。现在断言 id（`holders.top10Danger`），文案与逻辑解耦。

3. **数字格式跟着语言走。** `t()` 之外提供 `n()`，用 `toLocaleString` 按
   locale 格式化千分位。

#### 坑一：「文案里有条件分支」不能靠参数拼

分析器里有大量这种拼装：

```ts
`由 ${locker} 持有` + (unlockAt ? `，锁定至 ${unlockAt}` : '')
```

看起来可以直接写成 `由 {locker} 持有{unlockAt}`，**但不行**：后缀自带前置标点，
`unlockAt` 为空时会留下一个孤零零的逗号。而且英文语序未必相同。

处理方式分两类：
- **影响句子结构的**（有/无某个从句、主语不同）→ **拆成两个 id**，
  各写各的完整文案。本次共拆了 27 组，例如
  `lpLockedByLocker` / `lpLockedByProgram` / `lpLockedNoLocker`。
- **句末独立整句的**（前面是完整句、后面只是追加一句）→ 保留可选参数。

#### 坑二：派生占位符必须有实现，否则裸露在页面上

上一类里「自带标点的可选后缀」用 `{unlockAtText}` 这种占位符表达，
但它们**不在 `params` 里** —— 由 `src/i18n/finding.ts` 的
`derivePlaceholders()` 派生（返回空串时连标点一起消失）。

⚠️ 这是本次最危险的一处：任何派生占位符只要忘了实现，页面上就会出现
`{unlockAtText}` 这样的字样。所以有两条测试钉死它：
`派生的可选后缀占位符必须被本地化层填充，不能裸露` 与
`派生值不得覆盖分析器显式给的 params`。

#### 坑三：同一份文案有两份副本，就会漂移

雷达图的轴标签曾经**自带一份中文**（在 `visuals.tsx` 里），而其它区块走字典 ——
结果是英文界面下雷达图仍然显示中文。修法是让 `AXES` 只保留 `key`，
名字统一来自 `dimensions.<key>`。

**规则：界面上的每一处文案，全项目只能有一个来源。** 少一份副本就少一个漂移点。

#### 校验机制

- `findings.test.ts`：中英 key 集合必须完全一致（122 条 id / 244 个 key）、
  占位符同名、英文不得原样照抄中文、不得残留 `${}` 模板语法。
- `dimensions.test.ts`：每个维度都必须有中英文名 ——
  **新增维度忘了加译文会在这里失败**。
- `finding.test.ts`：回退行为（缺译文时用中文，绝不留空）。

#### 语言状态的取舍

放 `localStorage` 而不是 URL 路径：切换即时生效、不刷新、不会丢掉扫描结果
（结果在客户端状态里，换成 `/en` 路由会丢）。代价是分享链接不带语言。
首次访问按浏览器语言探测（`zh*` → 中文，其余 → 英文），之后记住用户的选择。
切换时同步更新 `<html lang>`，影响字体渲染与屏幕阅读器发音。


#### 覆盖面：连「采集告警」和「常量表」也要走字典

第一轮只把「界面文案」和「分析器结论」做了国际化，实测英文界面仍有
164 处中文。原因是中文还藏在三类地方：

1. **分析器的组合句**（`pieces.*`）。分析器把内联拼接的中文片段当作
   `params` 传给 UI，例如抛压的 `sellEvidence` 里含「，钱包 X，签名 Y」
   这类连接词。改成输出**结构化分片**，渲染层按语言组装。
2. **providers 的采集告警**（`warnings.*`，53 条）。`warnings: string[]`
   改为 `Warning[]`。⚠️ 这里有个安全点：`warn()` 的 `text`（中文回退）是
   **必填**的 —— 少一条告警会被读成「数据是全的」，不能因为国际化而丢。
3. **常量表里的展示名**。`AMM_PROGRAMS`（PumpSwap / Meteora DLMM …）、
   `CUSTODY_PROGRAMS`（Jupiter Lock）、盈亏分桶、holder kind 长短名。

第 3 类里 `CUSTODY_PROGRAMS` 的 `labelKey` 一开始没往
`HolderCustody → HolderRow → CustodyMetric` 这条链透传，结果英文界面
显示「Jupiter Lock（锁仓）」—— 类型系统帮不上忙，只能靠实测发现。

#### 三个「界面直接显示出一串 key」的坑

这三个都**不报错**：`t()` 缺 key 时返回 key 本身（刻意的设计，让漏译显眼），
所以类型检查、构建、以及「字典完整性」测试全部通过，只有真跑起来才看得见。

1. **扁平带点 key 写错了命名空间。**
   `findings` / `warnings` / `pieces` 是**刻意的扁平 Record**（key 自带全前缀，
   `lookup()` 有专门分支）。但 `report.common.*` 走的是分层查找。
   有人按前者的习惯把 holder kind 短名写成 `'pool.short'`，于是
   `holderKinds.pool.short` 永远查不到，界面直接显示这串 key。

2. **中文字典被从英文复制。** `pieces.zh.ts` 的 poolLabels 是英文，
   中文界面显示 `pump.fun bonding curve`。
   ⚠️「能查到」类测试**查不出**这个 —— 它能查到，只是语言错了。
   所以另加了一条「中文字典里不得出现与英文完全相同的成串英文」
   （豁免专有名词，以及 `{sol} SOL @ {time}` 这种纯数据模板）。

3. **告警参数本身是字典 key 列表。** AMM 池类型以
   `pieces.poolLabels.pumpswap,pieces.poolLabels.meteoraDlmm` 形式传入，
   需要 `localizeWarning` 二次解析，否则英文告警里夹着中文池类型名。

这三条现在都有 `src/i18n/keys.test.ts` 钉住。

**一条经验**：i18n 的测试全绿 ≠ 界面没有中文。
上面每个 bug 都是在**浏览器里扫一遍 innerText** 才发现的，
所以验收标准是「英文界面残留中文 = 0」，而不是「测试通过」。
