# Meme Radar · Pump.fun 买入风险体检

输入一个 Solana mint 地址，判断这个 meme coin **是否值得买入**、
以及**有哪些会让你血本无归的机制**。

五维链上风控 → 硬否决短路 → 仓位建议。带 Web UI、API 与测试。

> ⚠️ **本工具不构成投资建议。** 评分低只代表「未发现明显问题」，
> 不代表安全 —— meme 币归零是常态。

## 评分模型

```
总分 = Σ(维度风险分 × 权重)
```

| 维度 | 权重 | 硬否决项（一票判死） |
|---|---|---|
| 合约安全 | 30% | mint / freeze authority 未放弃；Token-2022 含 TransferHook / PermanentDelegate |
| 流动性 & 资金流 | 25% | 已抽池；买盘一边倒但卖单笔数 < 5%（蜜罐） |
| 持币集中度 | 20% | 剔除池/burn 后 Top10 > 40% |
| 开发者历史 | 15% | 历史 rug ≥ 2 次；dev 已清仓 |
| 社交热度 | 10% | 不做否决（仅叠加集中持仓时提权），上限压到 85 |

风险等级：`< 25` 低 · `25–45` 中 · `45–65` 高 · `> 65` 极高

**先跑硬否决，命中即短路。** 否决项是「一票判死」，此时再算加权分没有意义，
而且会给出「总分 60 好像还能小仓」的错误暗示。
命中否决时总分直接拉满 100，保证**分数与结论不矛盾**。


## 设计上的关键决策

这些来自对真实 rug 手法的调研，直接决定检测准不准。

**1. 持仓集中度必须先剔除池地址 —— 这是最大的误报源。**
bonding curve / AMM pool 天然持有大部分供应量。不先把池、金库、burn 地址剔除，
任何正常项目都会被算成「Top10 控盘 80%」。
`engine.test.ts` 里有一个测试专门证明这一步不可省：同一份数据，只要认不出池地址，
Top10 就从 20% 飙到 62% 并触发否决。

**2. 「买盘一边倒」可能是蜜罐，不是利好。**
看到买盘占 97% 容易以为是强势。但若**卖单笔数**极少（< 5%），
真实含义是「根本卖不出去」。所以必须**同时**看金额占比和笔数占比 —— 只看金额会漏报。
反过来，只看笔数也会误判：毕业瞬间的抢购笔数极高，并非刷量。

**3. 刷量要用「净 SOL 流入」而非「笔数」判定。**
高笔数 + 净流入 ≈ 0 才是对倒刷量。
进一步地，**笔数比与金额比背离**（买单笔数是卖单 2 倍，但买入金额不到卖出的一半）
说明「小额买盘撑笔数、大额卖盘出货」。

**4. 未知 ≠ 安全，也 ≠ 危险。这是本工具最花心思的部分。**
真实数据源经常只给一部分数据。如果把缺失当成 0，会得到两种致命错误：

- 把缺失当「安全」→ 报告显示绿色「低风险」，用户以为体检过了
- 把缺失当「危险」→ 凭空报出高风险，用户被吓跑

因此：每个分析器在数据缺失时**返回 `available: 0` 并说明缺失**，
引擎据此算出**数据覆盖率**；覆盖率 < 40% 时，
连**分数和等级一起作废**，显示「数据不足 · 无法评估」并**拒绝给出仓位建议**。

只改建议文案是不够的 —— 用户第一眼看的是那个绿色大数字，
它会直接盖过下面「数据不足」的提示。

**5. 权限必须读到 `null` 才算「已放弃」。**
`c.mintAuthority ? 0 : 1` 这种写法会把 `undefined`（没读到）当成「已放弃」，
在 UI 上渲染成绿色的安全标记。所以权限状态是**三态**的：
`1` = 已放弃，`0` = 未放弃，`-1` = 未知。

**6. 代币程序必须读 `getAccountInfo().owner`。**
`getParsedAccountInfo` 返回的 `parsed.info.owner` 是 **authority**，不是代币程序。
混淆这两者会导致「所有代币都用了 Token-2022」的严重误判。

**7. 不要把「账号新」等同于 bot。**
meme 玩家本来就开新钱包、新 X 号，真实社区早期账号质量也低。
判定要看**行为聚类**（同批账号反复同时出现在多个 meme 下），不是注册时间。

**8. dev 卖出部分 ≠ rug。**
部分回收成本在 meme 圈极常见。只有「清仓 + 时间很早」才升级为高危。

## 项目结构

```
src/
  core/
    types.ts              归一化数据契约（分析器只依赖它，不关心数据来源）
    constants.ts          风控阈值 + 协议固定标识 + 评分/分档工具
    engine.ts             编排五维 → 硬否决短路 → 加权总分 → 中文报告
    analyzers/
      contract.ts         合约安全：权限、Token-2022 扩展、转移税、LP 锁定
      liquidity.ts        流动性：抽池、刷量、蜜罐、抛压、狙击
      holders.ts          持币集中度：先分类剔除池/burn，再算占比
      developer.ts        开发者履历：历史 rug、批量发币、dev 清仓
      social.ts           社交热度：刷量识别（不做否决）
    engine.test.ts        26 个测试
  providers/
    sample.ts             6 个演示场景（健康 → 典型 rug 的光谱）
    solana.ts             Solana RPC：权限、Token-2022 TLV 扩展、最大持仓
    dexscreener.ts        市场数据：价格、成交量、买卖笔数、池地址
    index.ts              采集编排 + 优雅降级
  app/
    page.tsx              首页：地址输入 + 样本快捷入口
    api/scan/route.ts     POST /api/scan
    globals.css           主题与动画
  components/
    Report.tsx            报告：结论、否决置顶、五维明细、数据来源
    visuals.tsx           分数圆环 + 五维雷达图（手写 SVG，无图表库依赖）
```

**架构要点**：分析器只依赖归一化数据结构，不关心数据来源。
接入新数据源只需新增一个 provider，分析逻辑零改动。

## API

```bash
# 真实扫描
curl -X POST http://127.0.0.1:5273/api/scan \
  -H 'content-type: application/json' \
  -d '{"mint":"<mint address>"}'

# 样本
curl -X POST http://127.0.0.1:5273/api/scan \
  -H 'content-type: application/json' -d '{"sample":"honeypot"}'

# 列出样本
curl http://127.0.0.1:5273/api/scan
```

返回 `ScanReport`：`score` / `band` / `vetoed` / `vetoes` / `dimensions` /
`advice` / `coverage` / `meta`（数据来源与告警）。

## 数据来源与已知限制

界面上的「数据来源」面板会如实标注每个字段组是
**链上 / DexScreener / 推算 / 未采集**，`meta.warnings` 里列出所有采集告警。
请务必区分「链上事实」与「推算值」。

当前**未接入**（标记为未采集，不参与评分）：

- **社交热度** —— 需要 X/TG 数据服务，链上拿不到
- **开发者历史** —— 历史 rug 数、dev 卖出比例需要索引器回溯 creator 的发币记录
- **LP 锁定状态** —— RPC 无法直接判定，需解析锁仓程序或接 RugCheck

其它限制：

- 链上只能取前 20 大持仓账户，且**无法自动识别 AMM 池地址**，
  池持仓可能未被剔除，Top10 集中度会偏高（已在 warning 中提示）
- DexScreener 不直接提供买卖**金额**，当前按笔数比例拆分，属推算值
- bonding curve 虚拟储备、毕业阈值属协议内部常量，随版本变化，需运行时从链上读

**交叉验证渠道**：RugCheck、DexScreener、Solscan、Bubblemaps。
