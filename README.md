# Meme Radar · Pump.fun 买入风险体检

输入一个 Solana mint 地址，判断这个 meme coin **是否值得买入**、
以及**有哪些会让你血本无归的机制**。

五维链上风控 → 硬否决短路 → 仓位建议。**全部结论来自实时真实数据，没有任何模拟数据。**

> ⚠️ **本工具不构成投资建议。** 评分低只代表「未发现明显问题」，
> 不代表安全 —— meme 币归零是常态。

---

## 快速开始

```bash
npm install
cp .env.example .env.local     # 填入你的 Helius RPC / API key（见下）
npm run dev                    # → http://127.0.0.1:5273

npm test                       # 37 个测试
npm run typecheck
npm run build
```

### 配置数据源（必读）

本项目**只使用真实数据源**，因此必须配置一个可用的 RPC 端点。
公共节点 `api.mainnet-beta.solana.com` 限流极严重 ——
一次扫描要发十几次 RPC 调用，用公共节点几乎必然失败。**建议用 Helius。**

```bash
# .env.local
SOLANA_RPC_URL="https://mainnet.helius-rpc.com/?api-key=你的key"
HELIUS_API_KEY=""     # 可选：RPC URL 里带了 api-key 就不用重复填
```

页面顶部会显示**数据源能力自检**，明确告诉你当前配置下哪些维度能真正生效。

## 数据来源与维度覆盖

四个数据源，各司其职：

| 数据源 | 提供什么 | 需要 key |
|---|---|---|
| **Solana RPC** | mint 账户原始字节：mint/freeze 权限、Token-2022 TLV 扩展、最大持仓、bonding curve 账户（真实 SOL + 是否毕业） | 是（推荐 Helius） |
| **Helius DAS `getAsset`** | 名称、符号、图片、供应量、精度、代币程序、单价/市值、mint 扩展 | 是（同一个 key） |
| **Helius Enhanced API** | 部署者身份、逐笔买卖方向与金额、dev 持仓与卖出、历史发币、最早成交（狙击窗口） | 是（同一个 key） |
| **DexScreener** | 价格、市值、流动性 USD、AMM pair 地址 | 否（公开免费，可用时自动启用） |
| **RugCheck** | **LP 锁定/销毁比例与 LP 持有者**、持有人总数、AMM 池与金库账户、风险项 | 否（公开免费） |

对应的维度覆盖情况：

| 维度 | 权重 | 数据来源 | 无 Helius key 时 |
|---|---|---|---|
| 合约安全 | 30% | Solana RPC + DAS + RugCheck（LP 锁定/销毁） | RugCheck 不可达时 LP 状态标「未知」 |
| 流动性 & 资金流 | 25% | RPC 读 bonding curve 账户 + Enhanced API 逐笔成交（+ DexScreener 补 USD） | **标记未采集** |
| 持币集中度 | 20% | Solana RPC + PDA 推导 + RugCheck（持有人总数 / 池金库） | 可计算 |
| 开发者历史 | 15% | Enhanced API + 余额查询 | **标记未采集** |
| 社交热度 | 10% | 需 X/TG 第三方服务（**当前未接入**） | 不计分 |

只有 DexScreener 挂了不影响买卖结构：买卖笔数与金额来自 Helius 的逐笔成交，
RugCheck 还会补上持有人总数与池深度。反过来 RugCheck 挂了也只影响
「LP 锁定/销毁」与「持有人总数」两项，报告会明确标成「未知」并给出告警。

社交热度是唯一没有真实数据源的维度：Helius 不提供社交数据，
链上也拿不到社区质量。因此它**恒为「未采集」且不计入评分** ——
不会用任何替代值伪装成已检查。

### 硬否决项（一票判死）

| 维度 | 否决条件 |
|---|---|
| 合约安全 | mint / freeze authority 未放弃；Token-2022 含 TransferHook / PermanentDelegate |
| 流动性 | 买盘一边倒但卖单笔数 < 5%（蜜罐） |
| 持币集中度 | 剔除池/burn 后 Top10 > 40% |
| 开发者历史 | dev 已清仓 |
| 合约安全 | LP **已核实未锁定也未销毁**且由单一地址持有（可随时撤池） |

风险等级：`< 25` 低 · `25–45` 中 · `45–65` 高 · `> 65` 极高。
**命中否决时总分直接拉满 100** —— 保证分数与结论不矛盾。

## 设计上的关键决策

这些来自对真实 rug 手法的调研，直接决定检测准不准。

### 1. 池地址必须**推导**出来，不能靠正则猜 —— 最大的误报源

bonding curve / AMM pool 天然持有大部分供应量。不剔除，任何正常项目都会被算成
「Top10 控盘 80%」。

真实池地址是**随机 base58 字符串**，用 `/pool|vault|amm/` 这类正则去匹配
**几乎永远匹配不到** —— 只会让人误以为已经处理过了。所以 `pools.ts` 用确定性推导：

- pump.fun bonding curve PDA：`seeds = ["bonding-curve", mint]`
- **池的 ATA**：池持有代币用的是它的 associated token account，
  只认池地址会漏掉真正的持仓账户
- DexScreener 的 `pairAddress`（AMM 池地址的直接来源）
- RugCheck 的 `market.pubkey / liquidityA / liquidityB`：**真实存在**的池与金库账户
  （Raydium v4 之类独立 vault 只有它能给出）
- 持仓匹配时 **owner 与 token account 任一命中即算池**（只看 owner 会漏掉金库）

曾经还推导过 PumpSwap 池 PDA（`seeds = ["pool", index, creator, …]`）。
实测该推导对真实代币算出的地址在链上**并不存在**（建池者是迁移权限账户，
不是代币创建者）—— 一串「看起来很像池」的随机地址。未经校验的推导比没有更糟，
已删除。

`pools.test.ts` 锁住了这一点：同一份数据，认不出池就会误报庄家控盘。

### 2. 池地址不能靠「谁在卖币」来推断 —— 会把 dev 的筹码抹掉

看起来合理的一个启发式：买单里把代币交出来的账户就是池。
**这是错的**，而且错得很危险 —— 「AMM 池提供流动性」和「dev 在砸盘」
在成交数据里长得一模一样。

实测后果：某代币 creator 持有 **46%** 供应量，因为频繁卖出而被判成「池」
并从集中度里剔除，报告显示「持仓分布健康」，把一个高度控盘的币
**判成了安全**。这是比误报更糟的一类错误 —— 误报只是吓跑用户，
漏报会让人真的亏钱。

所以池地址只认**确定性推导**与**权威数据源**：PDA 推导、DexScreener 的 pair 地址、
RugCheck 给出的池与金库账户。
漏掉池会让集中度偏高（已在 warnings 里如实说明），这比抹掉真实筹码安全得多。

### 3. 「已清仓」只能由链上余额判定，不能由流水比例判定

同样是实测踩出来的：creator 用流水口径算出「卖出/买入 = 100%」，
但**链上余额还有 27.6% 供应量**，于是报出「部署者已清仓」的硬否决 ——
与事实完全相反。

原因：交易历史窗口有限（只取最近 100 笔），建仓与减仓可能落在不同窗口，
比例自然会失真。**余额是事实，流水只是推断。**
因此 `devFullyExited` 是三态的：`true` 已确认清仓 / `false` 已确认未清仓 /
`undefined` 无法确认。**只有 `true` 才允许触发硬否决。**

### 4. Token-2022 本身不是风险信号

想当然的判断是「pump.fun 走经典 SPL Token，用 Token-2022 就是仿冒」。
**实测发现新版 pump.fun 代币本身就发行在 Token-2022 上**（带 metadata_pointer 扩展）。
按老假设写会把**每一个正常新币**都打上 high 风险 —— 模型直接失去区分度。

真正的风险在扩展内容：`transferHook` / `permanentDelegate` 这类能限制卖出
或转走持币的扩展才是要害，逐项检查即可。

### 5. 未知 ≠ 安全，也 ≠ 危险 —— 本项目最花心思的部分

真实数据源经常只给一部分数据。把缺失当成 0，会得到两种致命错误：

- **把缺失当「安全」** → 报告显示绿色「低风险」，用户以为体检过了
- **把缺失当「危险」** → 凭空报出高风险，用户被吓跑

因此：每个分析器在数据缺失时返回 `available: 0` 并说明缺失原因，
引擎据此算出**数据覆盖率**；覆盖率 < 40% 时，
连**分数和等级一起作废**，显示「数据不足 · 无法评估」并**拒绝给出仓位建议**。

只改建议文案是不够的 —— 用户第一眼看的是那个绿色大数字，
它会直接盖过下面「数据不足」的提示。

**这个原则贯彻到了 provider 层**：RPC 读失败时返回 `contract: null`
而不是空对象 `{}`。返回 `{}` 会让「权限状态未知」冒充「已检查」，把覆盖率从 0% 抬到 30%。

### 6. 部署者 ≠ fee payer

Pump.fun 的交易由**用户钱包**签名，fee payer 往往是买家而不是发币人。
真正的部署者写在 Metaplex metadata 的 `creators` 字段里。
用 fee payer 当 creator 会追错人，整个「开发者历史」维度都是错的。

只有在 metadata 无 `creators` 时才回退到「发币交易的 fee payer」，
**并在 warnings 里明确标注这是推断值**。

### 7. 「买盘一边倒」可能是蜜罐，不是利好

看到买盘占 97% 容易以为是强势。但若**卖单笔数**极少（< 5%），
真实含义是「根本卖不出去」。所以必须**同时**看金额占比和笔数占比 —— 只看金额会漏报。
反过来只看笔数也会误判：毕业瞬间的抢购笔数极高，并非刷量。

### 8. 刷量要用「净 SOL 流入」而非「笔数」

高笔数 + 净流入 ≈ 0 才是对倒刷量。
进一步地，**笔数比与金额比背离**（买单笔数是卖单 2 倍，但买入金额不到卖出的一半）
说明「小额买盘撑笔数、大额卖盘出货」。

### 9. 权限必须读到 `null` 才算「已放弃」

`c.mintAuthority ? 0 : 1` 会把 `undefined`（没读到）当成「已放弃」，
在 UI 上渲染成绿色的安全标记。所以权限状态是**三态**：
`1` = 已放弃，`0` = 未放弃，`-1` = 未知。

### 10. 代币程序必须读 `getAccountInfo().owner`

`getParsedAccountInfo` 返回的 `parsed.info.owner` 是 **authority**，不是代币程序。
混淆这两者会导致「所有代币都用了 Token-2022」的严重误判。

### 11. dev 卖出部分 ≠ rug；账号新 ≠ bot

部分回收成本在 meme 圈极常见，只有「清仓 + 时间很早」才升级为高危。
同理，meme 玩家本来就开新钱包新 X 号，判定 bot 要看**行为聚类**而不是注册时间。

### 12. 不猜

拿不到的字段留空。「这个代币是不是 rug」需要价格与流动性历史，
单次 RPC 查询无法负责任地断言 —— 因此 `priorRugCount` **不猜**，
宁可留空也不用启发式编一个看起来确定的数字。

### 13. 声明了却没有任何 provider 写入的字段 = 死分支

比「猜」更隐蔽的一类错误：**schema 里有字段、分析器里消费了它，但没有一个
provider 会写它**。于是分支永远走同一条，结论永远同一种，而代码看起来
「检查过了」。

真实案例：`contract.lp.locked / burned` 与 `liquidity.lpLockedOrBurned`
从来没有任何数据源写入。后果是三重的：

1. **「LP 已销毁 / 已锁定」这两条好事永远不可能出现**（死代码）；
2. 每个有池的代币都固定背一条 high 风险「LP 锁定状态未知」，
   而真正的风险（LP 由单一地址持有、随时可撤）根本没被识别；
3. 同一事实在 `contract.ts` 与 `liquidity.ts` 各判一次，**重复扣分**。

修法是二选一，绝不允许「留着好看」：接真实数据源把它填上（现在由 RugCheck
提供 LP 比例与 LP 持有者），或者删掉字段与分支。同批清理的还有
`liquidityPulled` / `pulledLiquidity`（抽池没有前后快照可判）、
`fundedByMixer` / `hopCount`（跳数接口已下线）、`isTeamWallet`（没有资金图谱）、
`virtualSolReserves` / `graduationTargetSol` / `holderGrowth24h`（无来源），
以及 `priorTokens[].rugged`（要么真去回溯历史，要么别声称「记录干净」）。

**判据**：一个字段若只出现在 `types.ts`、分析器和 fixtures 里，
却从没出现在 `providers/` 的赋值语句右边 —— 它就是死字段。
对应的测试也补上了：`引擎测试 §9` 专门锁「字段没人写 ≠ 字段是 false」。

### 14. 「有账户」不等于「是钱包」—— 看 owner 程序，别看到账户就放行

判断一个持仓是个人还是程序托管，唯一可靠的判据是**账户的 owner 程序**：

| owner 程序 | 含义 |
| --- | --- |
| System Program (`1111…`) | 普通钱包 |
| Jupiter Lock | 时间锁仓（可读出解锁时间） |
| Squads 等 | 多签金库（**不剔除**） |
| AMM / 联合曲线 | 池子储备金库（按流动性剔除） |
| 查不到账户（PDA） | 回退：用 token account 创建交易反查 |

**踩过的坑**：旧代码把「owner 有账户」直接当成「普通钱包」而跳过。
但 Jupiter Lock 的 `VestingEscrow` **本身就是一个有数据的账户**（296 字节），
owner 正是 Lock 程序。结果 `9raUVuzeWUk…pump` 上那个占 **72% 供应量**的
锁仓仓位被当成普通巨鲸，报告给出「持仓集中度过高」的硬否决 —— 完全错误的结论。
修正后同一代币：否决消失，集中度从「过高」变为 **Top10 仅 8.2%**。

同理，池子也不该靠地址文本猜：用 **AMM 程序 id** 判定其拥有的账户是储备金库，
比正则可靠得多（实测某代币的 PumpSwap 金库占 5.15%，旧的池识别完全没认出来）。

### 15. 锁仓要剔除，但**多签不能剔除**，且剔除后必须列出来

「巨鲸 / 集中度」只应统计**能随时卖出**的筹码，所以时间锁仓必须剔除。
但这里有两个坑：

**坑一：多签不是锁仓。** Squads 这类多签金库可以随时凑齐签名转出，
把它当锁仓剔除 ＝ 把真巨鲸放过去，是危险的漏报。
因此 `EXCLUDED_HOLDER_KINDS` 只含 `pool / burn / timelock`，
`custody`（多签、未确认托管）**照常计入集中度**，只是单独标注。

**坑二：剔除不能变成「看不见」。** 被剔除的锁仓会单独列成一张表，
显示占比、控制程序和**解锁时间**，并明写「是否计入集中度」，
避免「悄悄扣掉一笔」变成隐性漏报。

判定方式（全部来自链上，不猜）：token account 的 authority 不是普通钱包
而是某个程序的 PDA —— 普通钱包一定有账户，PDA 没有账户；
再用该 token account **最早一笔交易里的 program id** 确认是哪个程序。

**只认已核实名单里的程序。** 早期版本把「交易里第一个非系统程序」当作
控制方，结果把某 pump.fun 代币的 5 个持仓标成「托管程序 DF1ow4…」，
而 `DF1ow4…` 实为 `SOLANA_PROGRAM_LIBRARY`（程序库），根本不是托管方。
**名字猜错比不标更糟**，所以名单外的程序一律不标注、不剔除。

**优先级：链上确认的事实 > 文本启发式。** 池标签只是拿地址字符串正则碰运气，
`custody` 是链上反查出来的确证事实。曾经把正则排在前面，
结果地址里带 `vault` 的已确认锁仓仓位被误判成池并静默剔除 ——
既没列出、也没算进集中度。

**解锁时间**：Jupiter Lock 的 `VestingEscrow` 布局已对着真实账户反推并交叉验证，
现在能给出**首次解锁**与**全部解锁**两个日期（例如实测某代币为
2026-10-01 → 2032-07-01，720,000,000 枚按月线性释放）。
三条独立校验支撑该偏移：

1. 托管账户 `[40:72]` 解出的 base58 **正好等于**它对应的 mint
2. `cliff_time − vesting_start_time` **正好等于 1 个 `frequency`**（30 天）
3. `cliff 额度 + 每期额度 × 期数` = **正好等于该账户实际持有的代币数量**

时间戳不合理（越界或全零）时**返回 null**，如实显示「待接入」，
绝不编一个日期出来。其它锁仓程序（Streamflow 等）尚未接入，同样标「待接入」。

## 项目结构

```
src/
  core/
    types.ts              归一化数据契约（分析器只依赖它，不关心数据来源）
    constants.ts          风控阈值 + 协议固定标识 + 评分/分档工具
    engine.ts             编排五维 → 硬否决短路 → 加权总分 → 中文报告
    analyzers/
      contract.ts         合约安全：权限、Token-2022 扩展、转移税、LP 锁定
      liquidity.ts        流动性：bonding curve 深度、刷量、蜜罐、抛压（+ 单位纪律）
      holders.ts          持币集中度：先分类剔除池/burn，再算占比（含狙击筹码）
      developer.ts        开发者履历：发币数量、dev 清仓（历史结局不猜）
      social.ts           社交热度：刷量识别（不做否决）
    fixtures.ts           测试夹具（仅测试用，不参与运行时）
    engine.test.ts        引擎与分析器测试
  providers/
    helius.ts             Solana RPC + DAS getAsset + Enhanced API（元数据/部署者/成交明细）
    pools.ts              曲线账户推导与解码（阶段 + 真实 SOL）、池 ATA 推导
    dexscreener.ts        市场数据：价格、成交量、买卖笔数、pair 地址
    rugcheck.ts           LP 锁定/销毁与 LP 持有者、持有人总数、池金库、风险项
    index.ts              采集编排 + 优雅降级
    pools.test.ts         池推导与曲线解码测试
    rugcheck.test.ts      RugCheck 映射测试（含 bonding curve 陷阱）
  app/
    page.tsx              首页：地址输入 + 数据源能力自检
    api/scan/route.ts     POST /api/scan、GET /api/scan（能力自检）
  components/
    Report.tsx            报告：结论、否决置顶、五维明细、数据来源
    visuals.tsx           分数圆环 + 五维雷达图（手写 SVG，无图表库依赖）
```

**架构要点**：分析器只依赖归一化数据结构，不关心数据来源。
接入新数据源只需新增一个 provider，分析逻辑零改动。

**关于测试数据**：`fixtures.ts` 只在单元测试里使用。
`src/providers/` 下全部是真实数据源，页面与 API 也只走真实链路 ——

## API

```bash
# 能力自检：当前配置下哪些维度可用
curl http://127.0.0.1:5273/api/scan

# 扫描
curl -X POST http://127.0.0.1:5273/api/scan \
  -H 'content-type: application/json' \
  -d '{"mint":"<mint address>"}'
```

返回 `ScanReport`：`score` / `band` / `vetoed` / `vetoes` / `dimensions` /
`advice` / `coverage` / `meta`（数据来源与告警）。

## 已知限制

界面上的「数据来源」面板会逐字段标注
**链上 / DexScreener / 推算 / 未采集**，`meta.warnings` 列出所有采集告警。
**请务必区分「链上事实」与「推算值」。**

- **社交热度无数据源** —— Helius 不提供，链上也拿不到，恒为「未采集」
- **历史 rug 数不计算** —— 需要价格与流动性历史，本工具只用单次查询；
  因此只报「发过几个币」，结局一律标为**未核实**，绝不输出「历史记录干净」
- **LP 锁定/销毁状态来自 RugCheck，不来自 RPC** —— RPC 拿不到「LP 在谁手里」。
  RugCheck 不可达、未覆盖该池、或该池的 LP mint 还没索引出来时，
  一律标「未知」并给出告警，**不会因为查不到就当成安全或危险**
- **bonding curve 的阶段与真实 SOL 来自链上账户的 `complete` 标志** ——
  不能用「账户是否存在」推断：实测已毕业代币的曲线账户常常仍然存在、
  余额被清空（据此判会得到「尚未毕业 + curve 内 SOL 0」两条假结论）
- **抽池检测未接入** —— 判定「资金被抽走」需要两次快照对比，
  单次扫描只能看到当下的池深度，因此不做这项判断
- **狙击占比是下限估计** —— 取最早 25 笔成交的付款方 ∩ 当前前 20 大持仓，
  只覆盖前 20 大窗口；拿不到最早成交时为「未知」，不是「没有狙击」
- **只有 Jupiter Lock 的解锁时间**已接入（布局经真实账户三重交叉验证）；
  Streamflow 等其它锁仓程序仍是「待接入」（**不是**「已解锁」）
- **AMM 程序 id 白名单**目前覆盖 pump.fun 曲线 / PumpSwap / Meteora DLMM /
  Raydium v4 / Raydium CPMM / Orca Whirlpool，均由 Helius `source` 独立核对过；
  新 AMM 出现前，其金库可能被计入集中度
- **托管程序只认已核实名单**（当前：Jupiter Lock、Squads 多签）——
  名单外的程序即使确认是程序控制，也**不标注、不剔除**，只计入告警计数；
  且只反查前 12 个疑似托管的持仓，其余按普通持仓处理（偏保守）
- **锁仓识别只看前 20 大持仓** —— 更小的锁仓仓位不在窗口内
- **链上只返回前 20 大持仓账户** —— 更深的分布需要索引器
- **部分 AMM 的 vault authority 无法推导**（如 Raydium v4 的独立 vault），
  这类池持仓可能未被剔除，会让 Top10 偏高；命中时会在 warnings 里提示
- **买卖笔数与金额来自 Helius 逐笔成交**（非 DexScreener 的聚合值），
  样本为最近 100 笔；代币刚开盘或交易极多时，该窗口不代表全历史
- **单位绝不混用**：SOL 口径的净流入/刷量只用逐笔成交算；
  DexScreener 的成交额是 USD，另存为 `buyVolumeUsd / sellVolumeUsd`，
  只参与与单位无关的占比判定（曾经把 USD 当 SOL，净流入虚高上百倍）
- **DexScreener 可能不可达**（网络/区域限制）—— 不影响买卖结构，
  但价格、市值、流动性 USD 会缺失，报告会如实标注「市场数据缺失」
- **部署者身份取自创建交易的 fee payer** —— 真实 pump.fun 代币的
  DAS `creators` 字段是空的，只能这样定位；若最早交易不是创建交易，
  会明确告警「可能是首个买家而非发币人」
- **dev 卖出比例受交易窗口限制** —— 因此「是否已清仓」一律以链上余额为准，
  余额查不到时只提示、不判死

**交叉验证渠道**：RugCheck、DexScreener、Solscan、Bubblemaps。
